# Enterprise Documentation Style Guide

**Reference ID:** STYLE-CORE-001
**Status:** Active
**Owner:** Enterprise Documentation Council
**Applies to:** All four supported document types

## Plain language

Use direct, concrete sentences. Put the actor before the action. Use one action, condition, or outcome per sentence when describing executable work. Define an acronym at first use and use the same spelling thereafter. Replace vague words such as “timely,” “appropriate,” “regularly,” and “as needed” with a measurable condition or a visible `TBD`.

## Normative language

Use `MUST` for an enforceable requirement, `MUST NOT` for a prohibition, `SHOULD` for a recommended practice, `SHOULD NOT` for a discouraged practice, and `MAY` for an allowed option. A normative statement has a stable requirement ID, applicability, accountable role, evidence expectation, and exception path.

## Headings and cross-references

Use one level-one title, then the section order in the selected template. Do not skip heading levels. Refer to stable IDs and exact section titles rather than “above” or “below.” A renamed object keeps its ID. A cross-reference that cannot be resolved is an issue, not an implied link.

## Tables and diagrams

Give each authoritative table a title, stable table ID, descriptive headers, units, period/as-of date, and source or owner. Do not put the only executable instruction in a screenshot. Mermaid is generated from structured objects; every node label references a stable ID and every diagram has an accessible caption and text explanation.

## Accessibility and review

Use sentence-case headings, short paragraphs, sufficient table context, and captions that explain the purpose of a figure. Keep examples fictional and label them clearly. Preserve `TBD`, open issues, and waivers instead of silently filling gaps. Reviewers score evidence, not polish alone.
